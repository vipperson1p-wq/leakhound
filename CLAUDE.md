# Vibe Scanner — инструкция для Claude Code

## Что это за проект
Сканер безопасности для вайбкод-проектов (Next.js / Vite + Supabase + Vercel).
Аудитория — люди, которые пишут код с помощью AI и плохо разбираются в безопасности.
Главное отличие от gitleaks / TruffleHog / Supabase Security Advisor:
- ловим проблемы в коде и миграциях ДО деплоя;
- объясняем простым языком;
- для каждой проблемы даём готовый промпт, который можно вставить в Cursor / Claude Code для исправления.

Язык интерфейса и отчётов — русский (позже добавим английский). Код и комментарии в коде — можно на английском.

## Текущее состояние (v0.1 + Фаза 1)
- `src/rules.js` — правила обнаружения (ключи, публичные env-переменные, .env в git, RLS в SQL).
- `src/scan.js` — движок: собирает файлы (через `git ls-files`, если это репозиторий) и применяет правила.
- `src/report.js` — вывод в терминал. `src/index.js` — CLI (`--json`, `--staged`, `--exclude`, `install-hook`).
- `src/ignore.js` — исключения (`.vibescanignore`), `src/hook.js` — pre-commit хук.
- `src/detectors/history.js` — `--history`: ключи, удалённые из файлов, но оставшиеся в истории git.
- `test/` — тесты (`npm test`). Фикстура вручную: `npm run scan:fixture`, самопроверка: `npm run scan:self`.
- `test-project/` — НАМЕРЕННО уязвимый проект с ФЕЙКОВЫМИ ключами для тестов. Не исправлять его. Исключать из самопроверки.
- Зависимостей нет, Node 18+. CI: `.github/workflows/ci.yml`.

## Главные принципы архитектуры (не нарушать)
1. **Обнаружение — только детерминированный код** (регулярки, парсинг). AI никогда не решает, есть уязвимость или нет.
2. **AI только объясняет**: отсеивает очевидные ложные срабатывания, пишет объяснение и промпт для исправления, отвечает в чате.
3. **Никогда не отправлять в AI сами секреты.** Только замаскированные фрагменты (`sk-pro…****`) и несколько строк контекста, не весь файл и не весь репозиторий.
4. **Ключи в любом выводе всегда маскируются** (терминал, JSON, база, логи).
5. **Сканируем только проекты пользователя**: локальную папку или репозиторий, к которому он сам дал доступ через GitHub. Никакого сканирования чужих сайтов/репозиториев по ссылке.
6. Модуль вызова AI — отдельная обёртка (`src/ai.js`), чтобы провайдера/модель можно было сменить в одном месте.
7. Код пользователей не хранить. В базе — только результаты (находки с замаскированными фрагментами).

### Фаза «Профессиональные правила» (сразу после подготовки к open source)
Цель — усилить проверки готовыми проверенными правилами вместо своих.

1. [ ] **Правила gitleaks.** Лицензия проверена: MIT, © 2019 Zachary Rice (`gitleaks/gitleaks`, правила в `config/gitleaks.toml`). Перенести правила с указанием авторства в `NOTICE` и сделать скрипт синхронизации. Учесть: регулярки gitleaks написаны для Go (RE2) — скрипт должен конвертировать синтаксис, который не поддерживается в JS на Node 18 (например, inline-флаги `(?i)`), и падать с понятной ошибкой на том, что сконвертировать нельзя. Каждое перенесённое правило — с тестом.
2. [ ] **Режим `--db` — через официальный Supabase CLI.** Решение владельца: `splinter.sql` **не копируем и не встраиваем** — у `supabase/splinter` нет лицензии (проверено 2026-10-03: нет файла LICENSE, бейдж в README битый). Владелец сам отправит Supabase issue с просьбой добавить лицензию.
   Вместо этого `--db` вызывает команду CLI **`supabase db advisors --local`** (проверено по исходникам `supabase/cli`, добавлена в PR #4957, первая версия — **v2.81.0**). Она запускает те же проверки, что Security/Performance Advisor в панели Supabase (нет RLS, открытый `auth.users`, SECURITY DEFINER-функции, неиндексированные внешние ключи и т.д.), прямо на локальной базе.
   - Как вызывать: `supabase db advisors --local --type all --output-format json` из корня проекта (CLI читает `supabase/config.toml`). Ответ — `{ results: Lint[] }`, где `Lint = { name, title, level (info|warn|error), facing, categories, description, detail, remediation, metadata?, cacheKey }`. Пустой результат: «No issues found» в stderr и `{ results: [] }`. Запрос выполняется в транзакции, которая всегда откатывается, — база не меняется.
   - Перевод в наш формат: `level` error → high, warn → medium, info → low (critical не ставим: это не утёкший ключ, а настройка базы); `ruleId` = `db:<name>`; `source: 'db'`; `title`/`detail`/`remediation` — как есть (английский) до AI-слоя; ссылка на документацию Supabase по `name`.
   - Только `--local`. **Никогда не вызывать `--linked` и `--db-url`** — это уже удалённая (возможно, продакшен) база и токен доступа; принцип «только локально, без наших серверов».
   - Миграции сами не применяем: `supabase start` применяет их при первом запуске, а `supabase db reset` **стирает локальные данные** — не запускать за пользователя. Если локальная база не запущена или CLI нет / версия ниже 2.81.0 — понятное сообщение, что сделать (`npx supabase start`), и обычный отчёт без `--db`.
   - Вызывать через `execFile` с массивом аргументов (без shell), с таймаутом. Супабейзовский CLI пишет телеметрию в `~/.supabase/telemetry.json` — упомянуть в README.
3. [ ] **Сверить список провайдеров с GitHub Secret Scanning.** Список поддерживаемых шаблонов — в документации GitHub (`github/docs`, лицензия CC-BY-4.0): сами форматы (префиксы токенов) — факты, но при заимствовании текста или таблиц — указать источник в `NOTICE`.

Не подглядывать в их реализацию при написании своих правил.

## Правила работы для Claude Code
- **Перед созданием платных ресурсов** (новый проект Supabase, платный план Vercel, покупка домена) — спроси меня и назови цену.
- **Перед деплоем в продакшен** — спроси меня.
- Никогда не коммить настоящие ключи. Все секреты — в переменных окружения Vercel/Supabase.
- Перед каждым коммитом: `npm test` и самопроверка сканером.
- Маленькие шаги: одна фича — один коммит с понятным сообщением.
- Если задача неясна — спроси, а не угадывай.
